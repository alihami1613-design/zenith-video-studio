# دروازه کیفیت و ممیزی ZENITH Desktop

این سند ممیزی اولیه شاخه `desktop-editor-foundation` است. هدف آن جلوگیری از معرفی قابلیت ناقص به‌عنوان قابلیت آماده است. این سند گزارش وضعیت مشاهده‌شده در کد و مستندات است؛ جایگزین اجرای تست یا تأیید روی Windows نیست.

## وضعیت ممیزی

- شاخه دسکتاپ مستقل از نسخه آنلاین است و نباید با `main` ادغام شتاب‌زده شود.
- مقایسه GitHub در زمان ممیزی: شاخه دسکتاپ 503 commit جلوتر و 11 commit عقب‌تر از `main` گزارش شده است؛ وضعیت دو شاخه `diverged` است.
- هویت برنامه در کد `APP_NAME = "ZENITH Desktop"` است.
- فایل CI موجود: `.github/workflows/desktop-model-tests.yml`.
- CI در push/PR مرتبط، `compileall` و `python -m unittest discover -s desktop_app -p "test_*.py"` را روی Python 3.11 و Ubuntu اجرا می‌کند و FFmpeg را برای تست‌های یکپارچه نصب می‌کند.
- تست‌های واحد مدل تایم‌لاین، ساخت فرمان رندر، صدا، رنگ، Scope، Proxy و تست‌های یکپارچه واقعی FFmpeg وجود دارند.
- در این ممیزی، تست‌ها روی Windows کاربر اجرا نشده‌اند؛ نتیجه سبز CI نیز هنوز در این گزارش تأیید نشده است.

## یافته‌های قطعی از کد

### اولویت بحرانی — جلوگیری از ازدست‌رفتن پروژه
- `new_project()` وضعیت فعلی را بدون پرسش ذخیره/رد تغییرات پاک می‌کند.
- مسیر `open_project()` پس از بارگذاری موفق، پروژه جاری را جایگزین می‌کند و پیش از آن تأیید تغییرات ذخیره‌نشده ندارد.
- در `main.py` مسیرهای ذخیره و بازکردن پروژه وجود دارند، اما پیاده‌سازی Auto-save و Crash Recovery در این فایل مشاهده نشد.
- هنگام ذخیره، فایل موقت و جایگزینی اتمیک استفاده شده است؛ این نکته مثبت است و باید حفظ شود.
- آزمون‌های خودکار مشخص برای چرخه کامل Save/Open رابط، هشدار تغییرات ذخیره‌نشده، بازیابی پس از crash و Relink رسانه در فهرست بررسی‌شده پیدا نشدند.

### اولویت بالا — محدودیت‌های خروجی
- اعتبارسنجی رندر فعلی نرخ فریم را به 25 یا 30 محدود می‌کند.
- ابعاد خروجی فعلی از 1920 پیکسل در هر ضلع بیشتر نمی‌شود؛ خروجی 4K در این نسخه پشتیبانی نمی‌شود.
- کدگذاری فعلی H.264 با preset سریع `ultrafast`، CRF 22 و حداکثر دو thread انجام می‌شود.
- رابط/مستندات باید کیفیت پیش‌نمایش را از کیفیت خروجی نهایی جدا کنند و تنظیمات رندر قابل انتخاب داشته باشند.
- گزارش پیشرفت و لغو رندر باید به‌عنوان قابلیت مستقل بررسی و آزمایش شوند.

### اولویت بالا — پیش‌نمایش و تدوین
- پیش‌نمایش رنگ، Scopeها و بعضی تحلیل‌ها نمونه‌برداری کم‌وضوح و با اجرای دستی هستند؛ معادل Program Monitor زنده و کامل نیستند.
- بعضی قابلیت‌های Transform، Mask، Blend و Keyframe در خروجی رندر اعمال می‌شوند، اما پیش‌نمایش زنده متناظر در همه مسیرها وجود ندارد.
- متر صوتی فعلی برآوردی از waveform cache است، نه متر لحظه‌ای پخش.
- مدیریت رسانه باید مسیرهای مفقود، Relink، مسیر نسبی، و کنترل فضای Cache را پوشش دهد.

### اولویت مهندسی — نگهداری‌پذیری
- `desktop_app/main.py` حدود 2,490 خط دارد و مسئولیت‌های UI، پروژه، صدا، رنگ، Proxy و رندر را کنار هم نگه می‌دارد.
- پیش از افزودن قابلیت‌های بزرگ، مرزبندی ماژول‌های Project/Media/Playback/Timeline/Render/Audio/Color و مدیریت خطا باید روشن شود.
- تغییرات ساختاری باید تدریجی، با حفظ سازگاری پروژه‌های قدیمی و تست مهاجرت schema انجام شوند.

### ناسازگاری مستندات
- `timeline_model.py` در ممیزی دارای `PROJECT_SCHEMA_VERSION = 25` است، درحالی‌که بخشی از `README_FA.md` هنوز به ساختار نسخه 7 اشاره می‌کند.
- README و ROADMAP باید یک منبع وضعیت واحد داشته باشند تا قابلیت قدیمی یا ناقص به اشتباه آماده معرفی نشود.

## ترتیب اصلاح پیشنهادی

1. **Project Safety:** تشخیص تغییرات ذخیره‌نشده، تأیید پیش از New/Open/Close، Auto-save زمان‌بندی‌شده، بازیابی امن و تست خرابی/قطع برق شبیه‌سازی‌شده.
2. **Media Integrity:** Relink، مسیرهای قابل‌انتقال، بررسی فایل‌های مفقود و مدیریت Cache با سقف/پاک‌سازی امن.
3. **Render Reliability:** صف رندر، پیشرفت، لغو، presetهای کیفیت، اعتبارسنجی خروجی و گزارش خطا؛ حفظ مسیر CPU و افزودن شتاب‌دهی فقط پس از تشخیص سازگاری واقعی.
4. **Playback & Preview:** تفکیک Source/Program Monitor، کیفیت Preview، همگامی صدا/تصویر، seek فریمی و پیام خطای کدک.
5. **Timeline Workflow:** انتخاب چندگانه، Ripple/Slip/Roll/Slide، لینک صدا و تصویر، قفل/مخفی‌سازی ترک و Undo/Redo کامل.
6. **Professional Color/Audio:** پیش‌نمایش منطبق با خروجی، LUT/Curves و scopes معتبر؛ EQ/Dynamics و مترهای واقعی با تست.
7. **Creative Intelligence:** تحلیل پروژه و پیشنهادهای توضیح‌پذیر؛ هیچ تغییری بدون تأیید صریح کاربر اعمال نشود.
8. **Release QA:** تست واحد، یکپارچه، رگرسیون، پروژه سنگین، رسانه خراب، مسیرهای فارسی/طولانی، و آزمون واقعی روی Windows 11 و RX 580.

## دروازه پذیرش هر قابلیت

قابلیت تنها زمانی «تکمیل‌شده» است که هر چهار شرط ثبت شده باشد:

- [ ] طراحی و معیار پذیرش روشن
- [ ] پیاده‌سازی واقعی و متصل به جریان کاری
- [ ] تست خودکار/یکپارچه مرتبط با نتیجه قابل بررسی
- [ ] تأیید دستی روی Windows و پروژه نمونه

تا پیش از عبور از این چهار شرط، وضعیت قابلیت «در حال توسعه» یا «نیازمند آزمون» باقی می‌ماند.

## محدودیت این ممیزی

این بررسی بر پایه فایل‌های شاخه GitHub و مستندات موجود انجام شده است. اجرای برنامه دسکتاپ، اجرای کامل تست‌ها، آزمون روی سخت‌افزار کاربر و بررسی خروجی‌های واقعی در این مرحله انجام نشده است. هیچ ادعایی درباره قبولی آن آزمون‌ها مطرح نمی‌شود.
